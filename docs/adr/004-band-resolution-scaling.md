# ADR-004: 判定死區參數的尺規與影像尺寸來源

## Status

Proposed

## Context

`line_counting` 的 `crossing_band_px` 是直接套用的像素值：設定檔寫多少，就是判定時的帶寬。
同一份設定跑在混解析度的 bucket 上，各攝影機得到的實際效果差很多——3840 寬的機器和 1920
寬的機器，同樣的像素值代表的實際距離差兩倍。

實測 `bucket_20260728_small` / 2026-07-28（508,345 列，8 台攝影機、7 台有計數線）。以
「人形 bbox 寬度中位數」當跨解析度可比的尺規（`overlay/analysis/scale_norm.py`，開發用
工具、不進版控）：

| 攝影機 | 畫面 | 肩寬中位數 | `20 px` 佔肩寬 |
|---|---|---:|---:|
| cam002 | 1920x1080 | 63 px | 31.9% |
| cam006 | 1920x1080 | 71 px | 28.2% |
| cam007 | 1920x1080 | 97 px | 20.7% |
| cam008 | 1920x1080 | 161 px | 12.5% |
| cam001 | 1920x1080 | 165 px | 12.1% |
| cam005 | 1920x1080 | 174 px | 11.5% |
| cam003 | 3840x2160 | 381 px | 5.2% |

同一個 `20 px` 在七台上代表 5.2% 到 31.9% 的人形比例，倍差 6.1。調參的人以為在調同一件
事，實際上不是。這 6.1 倍裡有一部分是解析度造成的、可以精確校正，本 ADR 處理的就是這一
部分（其餘部分見 Consequences）。

要做到就得知道每台攝影機的影像尺寸，而 `line_counting` 是純 CPU 套件、部署時不掛載影片，
自己拿不到。上游 `video_analyze` 一直有這個值：為了配置共享記憶體環形緩衝，
`services/video_reader.py` 的 `probe_frame_shape` 會讀每路第一個片段的首格取得
`(height, width)`，只是從來沒寫進 `tracking_results.parquet`。

後續還有兩件事要用到同一份資訊：判定死區的空間化（`zone_mapping`）與計數線的幾何合理性
檢查（線離畫面邊緣多遠——實測 cam007 的線畫在 y≈1050，距 1080 的底邊只有 29 px）。尺寸
來源的選擇因此不只影響本次變更。

## Options Considered

### Option A：以人形肩寬百分比為尺規

不換算解析度，改用「該攝影機當日人形 bbox 寬度中位數」當單位，設定值寫成佔肩寬的百分比。
這正是上表與 `overlay/sweep.py` 掃參數時實際採用的換算。

Advantages

- 更貼近真正想控制的量。想控制的是「多大的抖動要被吃掉」，那是相對人形的尺度，不是相對
  畫面寬度；它同時吸收了解析度與安裝高度／視角兩種變異。
- 上表 6.1 倍的差異幾乎全部消除，不只解析度那一層。

Disadvantages

- **尺規會隨當日資料變動**：中位數取自當天的追蹤結果，同一份設定跑不同日期會得到不同的
  實際死區，重跑同一天也可能因 ByteTrack 的不可重現性而略有差異。設定與行為不再是固定
  對應，出了問題無從回溯是設定改了還是尺規飄了。
- 空資料或人流極少的攝影機沒有可靠的中位數，要另立退化規則。
- 後續的幾何合理性檢查仍然需要真實影像尺寸（肩寬換算不出畫面邊界在哪），最後會變成兩套
  尺規並存。

### Option B：在 `camera_registry.yaml` 人工填影像尺寸

Advantages

- 改動最小，`video_analyze` 完全不用動，既有的 `tracking_results.parquet` 全部可以繼續用。
- registry 本來就是人工維護的設定，多兩個欄位不引入新機制。

Disadvantages

- **與實際影片不同步時無人察覺**：換了鏡頭、改了錄影參數而忘了改 registry，換算會靜默用
  錯係數。
- **後續的幾何檢查會失去鑑別力**：那項檢查是拿畫面尺寸去檢查人工標的線座標（線是不是畫
  到畫面外、離邊緣太近）。尺寸如果也是人工填的，「座標和尺寸不同源」這類最該抓到的錯誤
  恰好抓不到——兩邊一起填錯就一起錯得很一致。

### Option C：`line_counting` 自己讀影片 header

Advantages

- 尺寸來自影片本身，不可能與實際不符；只讀 metadata 不解碼，成本低。
- 不動跨套件的檔案契約，舊 parquet 照樣能跑。

Disadvantages

- **打破 `line_counting` 的部署設計**。它是純 CPU 套件，容器不裝 torch、不掛載影片；為了
  讀兩個整數要掛載整個 bucket 的影片，還要引入 opencv 這類解碼依賴。
- 只調整計數線幾何時本來只需重跑本階段、不必碰影片，這個性質會失去。

### Option D：`video_analyze` 把影像尺寸逐列寫進 parquet，下游以 1080p 為基準換算（採用）

`TRACKING_RESULTS_SCHEMA` 加 `frame_width`／`frame_height` 兩欄，值取自既有的
`frame_shapes`；`line_counting` 的參數更名為 `crossing_band_px_1080p`，執行時逐攝影機算
`實際 px = 基準值 × frame_width / 1920`。

Advantages

- 尺寸與座標**同源**：兩者都出自同一次 `video_analyze` 執行，幾何檢查因此驗得出「線畫到
  畫面外」這類真正的配置錯誤。
- 上游本來就開了影片、也早就有這個值，不新增任何探測成本。
- 設定與行為是固定對應：同一份設定 + 同一份 parquet 永遠得到同樣的死區，可回溯。
- 後續的空間死區與幾何檢查共用同一個來源，不會演變成兩套機制。

Disadvantages

- 變更跨套件的檔案契約，既有的 `tracking_results.parquet` 全部要重跑才能給
  `line_counting` 用。
- 每列重複存兩個常數欄位。
- 基準值換算只用寬度、線性，仍是近似（見 Consequences）。

## Decision

用 Option D，基準定為 1080p 的寬度 1920。

尺寸與座標同源是關鍵：這三個任務（本次的死區換算、後續的空間死區、幾何合理性檢查）裡有
兩個是在檢查人工標註的幾何對不對，尺寸一旦也變成人工填的（Option B），檢查就驗不出最該
抓的那類錯誤。Option A 的尺規更貼近想控制的量，但把「同一份設定的行為」綁在當日資料上，
可重現性的代價太大，而且解不掉幾何檢查對真實尺寸的需求。Option C 的成本落在部署形態上，
為兩個整數放棄 CPU-only 隔離不划算。

實作上的幾個決定：

- **換算只用寬度、線性**。寬高比在同一組解析度家族內固定（1920x1080、3840x2160 皆
  16:9），寬度已足以表達尺度；引入對角線或面積開根號不會更準，只會更難解釋。
- **換算做在 `services/line_map.py` 的逐攝影機迴圈**，`count_line_crossings` 收到的一律是
  換算後的實際像素。判定邏輯不需要知道「基準解析度」這個概念，`services/stats.py` 維持
  純幾何，ADR-001／ADR-003 的判定語義一字未動。
- **參數更名為 `crossing_band_px_1080p`，且對舊名 fail loud**。沿用舊名而改變語義的話，
  既有設定會被靜默套用另一種解讀（4K 上變成兩倍帶寬），沒有人會發現。`extra="forbid"`
  本來就會擋下舊名，但訊息看不出語義也變了，因此加一個 `model_validator(mode="before")`
  給出可操作的訊息。
- **缺欄位的舊 parquet 直接報錯，不給 fallback**。「找不到尺寸就當成 1080p」會讓 4K 攝影
  機靜默套用一半的死區，正是這次要消除的錯誤本身。
- **`frame_height` 這次用不到也一併寫入**。後續的幾何檢查需要它（判斷線離畫面邊緣多遠），
  分兩次改 schema 會讓已產出的 parquet 再失效一次、GPU 再重跑一次。
- **存成每列的欄位，不存 parquet 的 key-value metadata**。schema 常數本來就是明確的契約，
  加欄位沿用既有 pattern，下游的相容檢查就是一次欄位存在性判斷；走 metadata 要在
  `ParquetWriter` 建立時就固定、自己做 JSON 編解碼，還多出「metadata 有但某台缺」這種
  部分缺失的情境。代價是每列重複兩個常數，靠 dictionary 與 RLE 壓縮吸收。

## Consequences

Positive

- 一個以 1080p 表達的設定值在各解析度上代表同樣的實際距離；混解析度的 bucket 不必為此
  各調一套參數。上表的差異由 6.1 倍收斂到 3.0 倍（`20 px` 基準值：換算後 cam003 得到
  40 px，佔肩寬 10.5%，其餘六台維持 11.5%–31.9%）。
- 執行日誌逐攝影機記錄 `frame_width`、換算係數與換算後的實際像素，事後能確認換算對不對。
- `tracking_results.parquet` 從此帶著影像尺寸，後續的空間死區與幾何合理性檢查不必再各自
  想辦法取得。
- 沿用舊參數名、或拿缺欄位的舊 parquet 來跑，都會明確報錯而不是被靜默套用另一種解讀。

Negative

- **換算消除的只是變異來源的一部分，而且不是最大的那一部分。** 六台 1080p 攝影機彼此的
  肩寬中位數就差 2.76 倍（63 對 174），比這次消除的解析度效應（2.0 倍）還大——差額來自
  各機的安裝高度與視角。同一台攝影機內的透視變異也還在（人形大小 p90 比 p10 差 2.1 到
  4.5 倍）。這次的效果是**讓調參少掉一個系統性、可精確校正的干擾項**，不是讓一個全域參數
  在各攝影機上有一致的效果。
- **既有的 `tracking_results.parquet` 全部對 `line_counting` 失效**，要以新版
  `video_analyze` 重跑（GPU）才能繼續統計。
- **同一份舊 parquet 會出現 `zone_mapping` 照跑、`line_counting` 報錯的不對稱狀態。**
  `zone_mapping` 不讀這兩欄，輸入端也沒有欄位白名單，缺欄位對它沒有影響。這是 fail loud
  決策的直接後果，不是 bug。
- **參數更名是破壞性變更。** 版控裡原本的預設值是 0，非 0 的值只出現在 `overlay/` 的
  sweep 實驗，所以沒有既有設定是因為「更名」而改變行為；但別處另存的設定檔需要人工改名，
  且要重新確認原本的數值是針對哪個解析度調出來的。
- **換算機制本身不改變任何輸出**（基準值 0 換算後仍是 0），這一層的驗收只能靠測試與日誌。
  同一個 PR 另外把預設值由 0 改成 25（實測挑出的值，理由見 `line_counting/README.md`
  的「已知限制」），輸出因此會變——那是調參的效果，不是換算機制的效果，兩者的證據分開列
  在 PR 的 Verification。
- **上下游耦合變緊。** `frame_width` 從「上游內部用來配環形緩衝的值」變成下游硬性依賴的
  欄位，`video_analyze` 日後改動 schema 要考慮 `line_counting` 會不會直接崩。
- 每列多兩個常數欄位。實測 `bucket_20260728_small` / 2026-07-28（約 50.8 萬列）檔案由
  16,426,702 增為 16,428,242 位元組（+1.5 KB，+0.01%），dictionary 與 RLE 幾乎完全吸收
  （兩次列數略有差異，源自 ByteTrack 的不可重現性）。
