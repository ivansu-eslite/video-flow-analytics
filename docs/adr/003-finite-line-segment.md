# ADR-003: 計數線的有效長度

## Status

Accepted

## Context

[ADR-001](001-line-crossing-detection.md) 決定了「人站在線的哪一邊」怎麼判：取離腳底點
最近的那一段線，用**那一段所在的無限長直線**算帶號距離，再用 Schmitt trigger 判什麼樣
的變化算跨過一次。它的三個選項都建立在「無限直線」這個前提上，這個前提當時沒有被檢視。

（本 ADR 全文的「腳底點」指的是判定所用的那個點；其定義後由
[ADR-009](009-head-based-foot-point.md) 由「框底邊中點」改成「用 head 框推算的落腳點」，
本 ADR 的閘門邏輯不受影響。）

後果是計數線的長度在數字上沒有意義。線段本身的長度只用來挑「哪一段最近」，不影響側別，
也不影響計數。人走在線的兩端之外——門旁邊的牆邊、線的延伸方向上——照樣被判成從一側移到
另一側而計入進出。已實測確認：門線 `x∈[0, 20]`，人在 `x=30`（乃至 `x=5000`）由 `y=20`
走到 `y=0`，舊語意一律得 `in_count=1`。

而門口正是計數線最主要的使用場合，「門有多寬」是配置的人畫線時唯一能表達的東西，卻表達
不出來。實測一天的真實資料（`bucket_20260728_small` / 2026-07-28，508,345 列、7 台有計數
線的攝影機、8 條線，`crossing_band_px=0`）：8 條線裡有 3 條的數字受影響，總量由
`in=333 / out=314` 降為 `in=307 / out=288`（約 −8%），且集中在短線——長到幾乎橫跨整幅
畫面的線沒有「線外」可言，數字不變。

## Options Considered

### Option A：維持無限直線，線長只用來挑最近段

Advantages

- 不動任何程式，也不會有既有的線因為畫得比實際門框窄而變成少算。
- 沒有「穿過線段」這個額外概念，判定規則只有側別與 Schmitt trigger 兩層。

Disadvantages

- 線的長度不是判準，門旁邊牆邊走過的人照算。畫線的人沒有任何方式表達「只算走過這個門
  的人」。
- 短線配寬畫面時誤計最嚴重，而短線正是單一門口的常見畫法。

### Option B：逐格有效性閘門——腳底垂足沒落在最近段本體上時，該格不判側別

判側別前先看腳底點到最近段的垂足有沒有落在線段本體上（不是被夾到端點）。落在端點外的
那一格視為無效，不判側別，並清除已確認的側別。

Advantages

- 概念上很直接：「你不在這段線的正對面，就不算站在它的任何一側」。
- 解得掉牆邊誤計。

Disadvantages

- **會製造新的漏計，而且漏在最要緊的情境上。** 實測三組：

  | 情境 | 期望 | 舊語意 | 逐格閘門 | 事件級閘門 |
  |---|---|---|---|---|
  | 斜穿門，穿越前一格已在線段外（band=0／3） | (1,0) | (1,0) | **(0,0)** | (1,0) |
  | 線外接近 → 門口線段區域內駐留 → 進場（band=3） | (1,0) | (1,0) | **(0,0)** | (1,0) |
  | ㄇ 形轉角外楔形斜穿入 | (1,0) | (1,0) | **(0,0)** | (1,0) |

  第二列不能接受：門口駐留正是 ADR-001 引入 Schmitt trigger 要解的情境。清除狀態後要
  重新確認側別需要 `|d| > band`，人若在線段區域內重新進入有效範圍，第一個確認的側別會被當
  成起始側而靜默漏計。
- 要引入「無效格」這個新狀態，Schmitt trigger 變成三態。
- ㄇ 形的直角轉角外會產生一整個延伸到無限遠的 90° 無效楔形。
- 必須寫死「有效性只看 argmin 那一段」；改成「任一段有效即有效」會讓 ㄇ 形開口外 150px
  的人被判成內側。這是個很不好解釋、又不能動的實作細節。

### Option C：事件級相交閘門——側別翻轉時，要求軌跡真的穿過線段（採用）

側別判定與 Schmitt trigger 完全不動。在「committed 側別翻轉即一次跨越」之上再加一道
條件：自上一次確認側別以來，該 track 的逐格位移線段必須真的與計數線的**有限線段**
相交過。

Advantages

- 側別判定與去抖行為原封不動，ADR-001 的結論全部保留，只是多一道閘門。
- 上表三組防過度修正的情境全部維持原本的計數。相交發生在哪一格不重要，只要發生在
  「上次確認側別」到「這次翻轉」之間就算數，所以線段區域內駐留、掉幀、斜穿都不影響。
- 沒有新狀態要維護，閘門是既有 filter 上多一個條件。

Disadvantages

- 判別的是「前一格到這一格」的直線，不是實際走過的路徑。掉幀嚴重時那一格的直線與實際
  路徑可能不同。
- `band > 0` 時有殘留的假陽性（見 Consequences）。
- 相交判別式有退化情況要處理（軌跡恰好通過彎折頂點、共線），寫錯會安靜地漏算或多算。

## Decision

用 Option C。

線的長度應該是實質判準——畫線的人畫多寬，就只算走過那個寬度的人。Option A 讓這件事無法
表達，Option B 表達得出來但把 ADR-001 好不容易解掉的門口駐留又弄壞了。Option C 兩件事
都成立：牆邊走過不計，門口駐留後進場照計。

實作是 `services/stats.py` 的 `segment_crosses_polyline`（numpy N×S 向量化叉積測試）加上
`count_line_crossings` 裡的一個 filter 條件。相交判別式定為「proper 相交 ∪ 四個
on-segment 退化檢查」，兩邊都不能省：

- 只取 proper 相交（`d1*d2 < 0 且 d3*d4 < 0`），軌跡恰好通過 polyline 的彎折頂點時判
  False——ㄇ／V 形門口的正常穿越會漏算。
- 直接把判別式放寬成 `<= 0`，共線但不重疊也會判 True——沿著線的延伸方向在端點外走過
  （正是本次要擋的情境）會誤判為相交。

退化檢查用精確 `== 0` 比較、不引入 epsilon：座標是像素浮點，精確共線實務上只會在合成
測試資料出現。

## Consequences

Positive

- 線的長度成為實質判準，配置的人可以用線長表達「這個門有多寬」。
- ADR-001 的側別判定與 Schmitt trigger 一字未動，`crossing_band_px` 的語意不變，
  輸出 schema 不變，不需要新的設定參數。
- 牆邊、線的延伸方向上走過的人不再計入，短線配寬畫面的誤計消失。

Negative

- **線畫太短會漏算。** 這是「線長即門寬」的直接後果，但既有的線若畫得比實際門框窄，
  行為會從「多算」變成「少算」。標註時線要拉滿可通行寬度，這條規則寫進
  `line_counting/README.md`；標註工具本身的提示另開 issue。
- **`in` 與 `out` 不再平衡。** 從門進場、繞牆邊出去的人，改動後是 `in=1 / out=0`（舊
  語意是 1/1）。這是「只算真的走過門」的直接後果，不是 bug；看報表的人會問，所以寫進
  README 與本 ADR。
- **`band > 0` 時有殘留的假陽性。** 人在線段區域內反覆穿過線段累積了相交，之後繞端點外出
  造成側別翻轉，閘門會放行。他確實穿過線段，只是那次翻轉的方向被歸因於繞端點的那一次。
  嚴重度低，不另做處理。
- **位移線段是直線近似。** 閘門逐格檢查「前一格到這一格」的直線；極端掉幀下那一格的
  直線可能與實際路徑不同。相交發生在哪一格不重要，只要落在「上次確認側別」到「這次
  翻轉」之間即可，所以線段區域內駐留、掉幀都不影響閘門本身。
- **產物分辨不出演算法版本。** `line_map.py` 只快照 `camera_registry.yaml` 幾何，沒有
  演算法版本標記，舊語意與新語意的 `line_counts.parquet` 從檔案上看不出差別。本次的處置
  是直接汰換重產、不保留舊檔，不引入版本標記機制。
- **既有數字要能解釋落差。** `bucket_20260728_small` / 2026-07-28 的逐線前後對照留在
  issue #61 與其 PR 描述；已對外報過舊數字的話需要據此說明。
- ADR-001 的 Option A/B/C 都是在無限直線前提下比較的，該前提由本 ADR 修正；ADR-001 的
  其餘結論（含「勿改成全域 signed-side」的告誡）仍然有效。
