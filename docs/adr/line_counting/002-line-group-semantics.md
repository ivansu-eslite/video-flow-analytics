# ADR-002: 計數線群組（`line_group`）的語意

## Status

Accepted

## Context

要統計的對象常是「一個區域範圍的進出」，而這種範圍通常不只一個出入口——一個樓層、
一個賣場區域會有好幾個門，還可能分屬不同攝影機。一個出入口本身就是一條計數線，多個
出入口合起來才構成這個範圍的進出。

目前 `line_counts.parquet` 的維度是 `camera_id` / `line` / `time_bucket`，一條計數線
就是一筆獨立統計，沒有辦法表達「這幾個門合起來是同一個範圍」，只能在報表端靠人工記憶
哪幾條線該加在一起。

本次讓 `Line` 帶一個 `line_group` 欄位標示它屬於哪個範圍，並把這個標示帶進統計輸出，
讓後續要做範圍層級彙總時有可依據的維度。彙總本身不在本次範圍——這裡只決定「群組要怎麼
定義、怎麼驗證」，不決定「怎麼加總」。

## Options Considered

這裡有兩個各自獨立的決策點：群組內怎麼加總、`line_group` 要不要驗證跨攝影機唯一。

### 決策一：群組內怎麼加總

#### Option A：各出入口的 in/out 直接相加

Advantages

- 範圍內各出入口理論上互不重疊，同一個人一次進出只會經過其中一個門，相加即正確。
- 不需要額外的跨線 track 關聯邏輯，實作即現有的每線獨立統計，群組只是多帶的標籤。

Disadvantages

- 若配置錯誤讓兩條線的偵測範圍實際重疊，或同一人連續穿過同群組的兩條線（例如在賣場
  內部從一個出入口走到緊鄰的另一個出入口），相加會重複計數。

#### Option B：先判斷同一人是否連續穿過同群組的兩條線，去重後再加總

Advantages

- 能處理 Option A 的重複計數邊界情況。

Disadvantages

- 需要跨線關聯同一 track 的穿越事件，複雜度高（要對照不同計數線間的 track_id 與
  時間先後）。
- 「連續穿過同群組兩條線」在正常配置下發生率低——出入口通常物理上分開、不會緊鄰到讓
  同一人連續刷過兩條，為低機率情境換取的複雜度不划算。

### 決策二：`line_group` 要不要比照 `line`／`zone` 驗證跨攝影機唯一

#### Option A：驗證跨攝影機唯一（比照 `line`／`zone`）

Advantages

- 與既有兩條規則（`zone`／`line` 名稱皆全域唯一）一致，實作與心智模型統一。

Disadvantages

- 會讓分組功能直接失效。一個賣場的數個門本來就分屬不同攝影機，要能歸成同一組，跨
  攝影機同名 `line_group` 正是這個功能存在的理由，不是需要擋下的錯誤。

#### Option B：不驗證跨攝影機唯一（採用）

Advantages

- 允許同一範圍的出入口分屬不同攝影機仍歸成同一組，符合這個欄位存在的目的。
- `line` 名稱本身仍全域唯一，因此 `(line_group, line)` 的組合天然唯一，不會有「同一條
  線被算進兩個群組」的疑慮。

Disadvantages

- 與 `zone`／`line` 的既有規則刻意相反，是後人最容易「順手」改壞的一點——見 Decision
  與 Consequences。

## Decision

決策一用 Option A：採相加，不做跨線去重。群組的語意就是「各出入口相加」；不處理同一人
連續穿越同群組兩條線的情況，這假設各出入口物理上不重疊、正常動線不會連續穿過同組兩條線。

決策二用 Option B：`line_group` 不驗證跨攝影機唯一，刻意與 `zone`／`line` 的規則相反。

另外定兩件實作細節：

- **`Line` 新增 `line_group: str`，必填。** 欄位名兩邊（yaml 與 parquet）統一用
  `line_group` 而非 `group`——`group` 是 BigQuery 與多數 SQL 的保留字，argus 那邊有
  BigQuery/Looker pipeline，先避開省得日後每次引用都要 backtick 或改資料契約。
- **本次只在輸出多帶 `line_group` 欄位，不做範圍層級彙總。** 彙總是後續任務，這裡只決定
  群組要怎麼定義、怎麼驗證，不決定怎麼加總。

## Consequences

Positive

- 後續要做範圍層級彙總時，`line_counts.parquet` 已有可依據的維度，不需要再補一輪資料
  遷移或回填。
- `(line_group, line)` 天然唯一，不需要額外的組合唯一性驗證。

Negative

- **方向配置錯誤不會被任何驗證擋下，而且會延後才爆。** 一個範圍的進出是把該範圍各出入
  口的 `in`／`out` 相加，這只有在每個出入口的 `inside_point` 都指向該範圍的內側時才成
  立。某個門的 `inside_point` 指反了，從那個門進來的人會被記成 `out`，加總後同時少算
  進、多算出，且不會有任何錯誤訊息。`vfa_registry` 驗不出這件事——它只知道
  `inside_point` 不能落在線段的延伸線上，無從得知哪一側才是「這個範圍的內側」。本次不
  做彙總，所以錯誤在這個 PR 的輸出上看不出來——每條線各自的數字都「對」，要等到後續做
  範圍加總時才會顯現。緩解只能靠標註頁的方向箭頭與文件（見 `line_counting/README.md`），
  程式擋不住。
- **必填欄位是破壞性變更。** `camera_registry.yaml` 不進版控，使用者手上其他份 registry
  要自己補 `line_group` 才能跑。
- **`line_group` 刻意不驗證跨攝影機唯一，是最容易被後人改壞的一點**：「順手」把
  `parse_and_validate_zones`／`parse_and_validate_lines` 的同型驗證套用到 `line_group`
  會讓分組功能直接失效，且只有測試會發現。`parse_and_validate_lines` 的 docstring 與
  `Line` 的欄位說明都直接寫明這一點並指向本 ADR。
- **不做跨線去重**假設各出入口物理上不重疊、正常動線不會連續穿過同群組兩條線；若日後
  出現這類場景，本 ADR 的相加語意需要重新評估。
